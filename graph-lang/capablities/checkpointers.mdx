# Checkpointers

checkpointer在每个超级步骤中保存图状态的快照，并组织到线程中。使用checkpointer编译一个图，以启用human-in-the-loop工作流、时间旅行调试、容错执行和会话内存。

<small>
使用agent服务器时agent服务器自动处理checkpoint，你不需要手动实现或配置checkpointers。服务器在幕后为你处理所有持久化基础设施
</small>
:::

<small>

</small>

## 为什么使用checkpointers
以下功能需要Checkpointer：
- Human-in-the-loop:：Checkpointer允许人类检查、中断和批准图步骤，从而促进了Human-in-the-loop工作流。这些工作流需要Checkpointers，因为人必须能够在任何时间点查看图的状态，
  并且图必须能够在人对状态进行任何更新后恢复执行。示例请参见中断。
- 记忆：Checkpointers允许交互之间的“记忆”。在重复的人类交互(如对话)的情况下，任何后续消息都可以发送到该线程，该线程将保留其对先前消息的记忆。有关如何使用checkpointers添加和管理会话记忆的信息，
  请参阅<a href='/graph-lang/capablities/memory'>添加记忆</a>。
- 时间旅行：Checkpointers允许“时间旅行”，允许用户回放之前的图执行，以查看和/或调试特定的图步骤。此外，Checkpointers使得在任意Checkpoints分叉图状态以探索替代轨迹成为可能。
- 容错：Checkpoint提供容错和错误恢复：如果一个或多个节点在给定的超级步骤失败，你可以从最后一个成功的步骤重新启动图。
- 待定写入：当一个图节点在给定的超级步骤执行过程中失败时，LangGraph会存储来自在该超级步骤成功完成的任何其他节点的待定checkpoint写入。当你从该超级步骤恢复图执行时，你不会重新运行成功的节点。


## 核心概念
### 线程
线程是分配给checkpointer保存每个checkpoint的**唯一ID或线程标识符**。它包含一系列运行的累积状态。当执行运行时，助手的底层图的状态将持久化到线程。

当使用checkpointer调用图时，你必须在配置的`configurable`部分指定`thread_id`：
```python
{"configurable": {"thread_id": "1"}}
```
可以检索线程的当前和历史状态。要持久化状态，必须在执行运行之前创建一个线程。LangSmith API提供了几个端点，用于创建和管理线程和线程状态。有关更多详细信息，请参阅API参考资料。

**checkpointer使用`thread_id`作为存储和检索checkpoints的主键**。没有它，checkpointers无法保存状态或在中断后恢复执行，因为checkpointers使用thread_id加载保存的状态。

#### 选择如何继续一个线程
thread_id标识保存的状态。输入和`checkpoint_id`确定调用是开始新工作、恢复未完成的工作还是重放历史记录。单独重用线程ID并不意味着执行恢复。

使用checkpointer和现有线程，为你的目标选择调用：
| 目标 | 调用 |  执行|
|---|---|---|
| 提交新输入   | graph.invoke(input, config)  | 将输入应用于已保存状态，并从入口点开始。  |
| 出错后继续   | graph.invoke(None, config)   | 加载最新的checkpoint并重试未完成的工作。省略checkpoint_id。 |
| 回复中断     | graph.invoke(Command(resume=answer), config)  | 提供中断的返回值。被中断的节点重新开始。  |
| 回放历史记录  | graph.invoke(None, snapshot.config)  | 使用get_state_history()中的快照，并在该checkpoint之后重新执行节点。  |

新输入不会清除线程。LangGraph使用state的reducer来应用它。使用新的thread_id则会以空状态开始。

当最新checkpoint没有未完成的工作时，Resume返回保存的结果，而不运行节点。有关可运行的示例，请参阅<a href='/graph-lang/capablities/interrupts'>恢复中断</a>和
<a href='/graph-lang/capablities/time-travel'>重放历史记录</a>。有关包装另一个框架时的入口点恢复规则，请参阅Functional API概述。

### Checkpoints
**线程在特定时间点的状态称为checkpoint**。checkpoint是在每个超级步骤保存的图状态的快照，由`StateSnapshot`对象表示(有关完整字段引用，请参阅StateSnapshot字段)。

#### Super-steps
LangGraph在每个超级步骤边界创建一个checkpoint。超级步骤是图中的一个“滴答”，其中为该步骤调度的所有节点都在执行(可能并行执行)。对于像START->a->B->END这样的顺序图，
输入、节点a和节点B都有单独的超级步骤——在每个步骤之后都会产生一个checkpoint。了解超级步骤边界对于时间旅行很重要，因为你只能从检查点(即超级步骤边界)恢复执行。

除了超级步骤checkpoint，LangGraph还在节点(任务)级别持久化写入。当超级步骤中的每个节点完成时，其输出将作为链接到正在进行的checkpoint的任务条目写入checkpointer的checkpoint_writes表。
这些按任务写入是启用待定写入恢复的原因：如果同一超级步骤中的另一个节点发生故障，成功节点的写入已经持久化，不需要在恢复时重新运行。一旦超级步骤完成，就会提交完整状态快照。

LangGraph还可以在超级步骤中保存单个节点执行的写入。**这些写入被存储为任务并用于容错**：如果同一超级步骤中的另一个节点发生故障，则恢复时不需要重新计算成功的节点写入。
这些任务写入不是完整的StateSnapshot checkpoint，因此时间旅行从超级步骤边界的完整checkpoint恢复。

Checkpoints是持久的，可用于在以后恢复线程的状态。

让我们看看调用简单图时保存了哪些checkpoints，如下所示：
```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langchain_core.runnables import RunnableConfig
from typing import Annotated
from typing_extensions import TypedDict
from operator import add

class State(TypedDict):
    foo: str
    bar: Annotated[list[str], add]

def node_a(state: State):
    return {"foo": "a", "bar": ["a"]}

def node_b(state: State):
    return {"foo": "b", "bar": ["b"]}


workflow = StateGraph(State)
workflow.add_node(node_a)
workflow.add_node(node_b)
workflow.add_edge(START, "node_a")
workflow.add_edge("node_a", "node_b")
workflow.add_edge("node_b", END)

checkpointer = InMemorySaver()
graph = workflow.compile(checkpointer=checkpointer)

config: RunnableConfig = {"configurable": {"thread_id": "1"}}
graph.invoke({"foo": "", "bar":[]}, config)
```
运行图表后，将有4个checkpoints：
- 空Checkpoint，START作为下一个要执行的节点
- Checkpoint，用户输入 `{ 'foo': '', 'bar': [] }` 和node_a作为下一个要执行的节点
- Checkpoint, 输出node_a `{ 'foo': 'a'，'bar': ['a'] }` 和node_b作为下一个要执行的节点
- Checkpoint的输出为node_b `{'foo'： 'b'，'bar'：['a'，'b'] }`， 并且没有要执行的下一个节点

请注意，bar通道值包含来自两个节点的输出，因为此示例具有bar通道的reducer。

#### Checkpoint命名空间
每个checkpoint都有一个checkpoint_ns(checkpoint命名空间)字段，用于标识它属于哪个图或子图：
- ""(空字符串)：checkpoint属于父(根)图。
- "node_name:uuid"：checkpoint属于作为给定节点调用的子图。对于嵌套子图，名称空间用|分隔符连接(例如，“outer_node:uuid|inner_node:uuid”)。

你可以通过配置从节点内访问checkpoint命名空间：
```python
from langchain_core.runnables import RunnableConfig

def my_node(state: State, config: RunnableConfig):
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
    # "" for the parent graph, "node_name:uuid" for a subgraph
```

有关使用子图状态和checkpoint的更多详细信息，请参阅<a href='/graph-lang/capablities/subgraphs'>子图</a>。


## 获取和更新状态

### 获取状态
与保存的图状态交互时，必须指定线程标识符。你可以通过调用graph.get_state(config)来查看图的最新状态。这将返回一个StateSnapshot对象，该对象对应于与配置中提供的线程ID关联的最新checkpoint，
或者与线程的checkpoint ID关联的checkpoint(如果提供的话)。
```python
# get the latest state snapshot
config = {"configurable": {"thread_id": "1"}}
graph.get_state(config)

# get a state snapshot for a specific checkpoint_id
config = {"configurable": {"thread_id": "1", "checkpoint_id": "1ef663ba-28fe-6528-8002-5a559208592c"}}
graph.get_state(config)
```
在这个例子中，get_state的输出如下：
```python
StateSnapshot(
    values={'foo': 'b', 'bar': ['a', 'b']},
    next=(),
    config={'configurable': {'thread_id': '1', 'checkpoint_ns': '', 'checkpoint_id': '1ef663ba-28fe-6528-8002-5a559208592c'}},
    metadata={'source': 'loop', 'writes': {'node_b': {'foo': 'b', 'bar': ['b']}}, 'step': 2},
    created_at='2024-08-29T19:19:38.821749+00:00',
    parent_config={'configurable': {'thread_id': '1', 'checkpoint_ns': '', 'checkpoint_id': '1ef663ba-28f9-6ec4-8001-31981c2c39f8'}},
    tasks=()
)
```
#### 状态快照字段
| 字段 | 类型 |  描述 |
|---|---|---|
| values        | dict             | 此checkpoint的状态通道值。  |
| next          | tuple[str, ...]  | 接下来要执行的节点名称。空`()`表示图已完成。 |
| config        | dict             | 包含`thread_id`, `checkpoint_ns`, 和`checkpoint_id`. |
| metadata      | dict             | 执行元数据.包含`source` `("input", "loop", or "update")`, `writes` (节点输出), 和 `step` (super-step数量).  |
| created_at    | str              | 创建此checkpoint的ISO 8601时间戳。  |
| parent_config | dict             | 上一个checkpoint的配置。第一个checkpoint没有。 |
| tasks         | tuple[PregelTask, ...]  | 此步骤要执行的任务。每个任务都有`id`、`name`、`error`、`interrupts`和可选的`state`(子图快照，当使用`subgraph=True`时)。  |


### 获取状态历史
你可以通过调用graph.get_state_history(config)来获取给定线程的图执行的完整历史记录。这将返回与配置中提供的线程ID关联的StateSnapshot对象列表。
重要的是，checkpoints将按时间顺序排列，最新的checkpoint/StateSnapshot是列表中的第一个。
```python
config = {"configurable": {"thread_id": "1"}}
list(graph.get_state_history(config))
```

#### 查找特定checkpoint
你可以过滤状态历史记录，以查找符合特定条件的checkpoint：
```python
history = list(graph.get_state_history(config))

# Find the checkpoint before a specific node executed
before_node_b = next(s for s in history if s.next == ("node_b",))

# Find a checkpoint by step number
step_2 = next(s for s in history if s.metadata["step"] == 2)

# Find checkpoints created by update_state
forks = [s for s in history if s.metadata["source"] == "update"]

# Find the checkpoint where an interrupt occurred
interrupted = next(
    s for s in history
    if s.tasks and any(t.interrupts for t in s.tasks)
)
```

#### 列出每个线程
要查看Checkpointer保存的每个线程的状态，例如构建管理或调试视图，请在列出checkpoint时省略thread_id：

graph.get_statehistory(config)在config中需要一个thread_id，并且只返回一个线程的历史记录。在你传递给编译的同一个checkpointer上调用.list，并且config=None：
```python
# config=None returns checkpoints across every thread
for checkpoint_tuple in checkpointer.list(None):
    print(checkpoint_tuple.config["configurable"]["thread_id"])
```
传递`none`，不是｛｝。`SqliteSaver`将任何非None配置视为线程过滤器，并在缺少`thread_id`时引发。对于异步图，请改用`.alist(None)`。这适用于InMemorySaver、SqliteSaver和PostgresSaver。
`.list`仍然为每个checkpoint返回一行，而不是为每个线程返回一行。因此，你可以自己按thread_id分组以构建线程列表。

### 回放
Replay重新执行前一个checkpoint的步骤。使用之前的checkpoint_id调用图，以在该checkpoint之后重新运行节点。跳过checkpoint之前的节点(其结果已保存)。
checkpoint重新执行后的节点，包括任何LLM调用、API请求或中断，它们在回放期间总是被重新触发。

有关回放过去执行的完整详细信息和代码示例，请参阅<a href='/graph-lang/capablities/time-travel'>时间旅行</a>。

### 更新状态

你可以使用update_state编辑图形状态。这将创建一个具有更新值的新checkpoint，而不会修改原始checkpoint。更新被视为与节点更新相同：值在定义时通过reducer函数传递，因此具有reducer的通道会累积值而不是覆盖它们。

你可以选择指定as_node来控制更新来自哪个节点，这会影响下一个执行的节点。有关详细信息，请参阅时间旅行：as_node。

## 持久化模式
LangGraph支持三种持久化模式，使你能够平衡性能和数据一致性。你可以在调用任何图执行方法时指定持久化模式：
```python
graph.stream(
    {"input": "test"},
    durability="sync"
)
```
从最不持久到最持久的持久化模式如下：
- 退出：LangGraph仅在图执行退出时(成功退出、出现错误或由于人在循环中断)才保留更改。这为长时间运行的图提供了最佳性能，但意味着中间状态不会被保存，因此你无法在执行过程中从系统故障(如进程崩溃)中恢复。
- 异步：LangGraph在执行下一步时异步保存更改。这提供了良好的性能和持久性，但如果进程在执行过程中崩溃，LangGraph不写入checkpoints的风险很小。
- 同步：LangGraph在下一步开始之前同步保存更改。这确保了LangGraph在继续执行之前写入每个checkpoints，以牺牲一些性能开销为代价提供了高持久性。

### 新线程上的第一个持久checkpoint
对于新线程，持久化模式还确定在第一个用户节点执行之前提交哪些checkpoint。内部__start__超级步首先运行；步骤0是在该超级步骤之后写入的循环checkpoint。
- 退出：在运行结束之前不存在checkpoint。运行过程中的崩溃不会留下线程的记录。
- 异步：LangGraph在第一个用户节点执行之前开始写入输入checkpoint，但不会等待写入完成。第一个用户节点可以在提交任何checkpoint之前运行。
- 同步：LangGraph在第一个用户节点执行之前提交输入checkpoint(步骤-1)和步骤0checkpoint。

:::warning
<small>
在每种模式下，第一个checkpoint变得持久之前的崩溃会使线程与从未被调用的线程无法区分：get_tuple()在这两种情况下都返回None，invoke(None，config)会引发EmptyInputError。
如果需要区分“从未接受”和“已接受但丢失”，请在checkpointer之外记录准入，例如在调用invoke之前将发件箱行提交到自己的存储中。
</small>
:::

## 优化checkpoint存储
默认情况下，LangGraph checkpoint在每个超级步骤写入每个状态通道的完整值。对于具有大量累积的长时间运行的线程(如多轮对话)，这可能会随着时间的推移产生显著的存储增长。

`DeltaChannel`只存储增长的增量，而不是完整的累积值，从而大大减少了附加重通道的checkpoint大小。有关使用情况和存储与延迟的权衡，请参阅DeltaChannel。

:::warning
<small>
DeltaChannel要求langgraph>=1.2，目前处于beta(测试阶段)。API可能会在未来版本中更改。
</small>
:::
