# Checkpointers

checkpointer在每个超级步骤中保存图状态的快照，并组织到线程中。使用checkpointer编译一个图，以启用human-in-the-loop工作流、时间旅行调试、容错执行和会话内存。

</small>
:::

</small>

## 为什么使用checkpointers
以下功能需要Checkpointer：
- Human-in-the-loop:：Checkpointer允许人类检查、中断和批准图步骤，从而促进了Human-in-the-loop工作流。这些工作流需要Checkpointers，因为人必须能够在任何时间点查看图的状态，
  并且图必须能够在人对状态进行任何更新后恢复执行。示例请参见中断。
- 记忆：Checkpointers允许交互之间的“记忆”。在重复的人类交互(如对话)的情况下，任何后续消息都可以发送到该线程，该线程将保留其对先前消息的记忆。有关如何使用checkpointers添加和管理会话记忆的信息，
  请参阅<a href='/graph-lang/capablities/memory'>添加记忆</a>。
- 时间旅行：Checkpointers允许“时间旅行”，允许用户回放之前的图执行，以查看和/或调试特定的图步骤。此外，Checkpointers使得在任意Checkpoints分叉图状态以探索替代轨迹成为可能。
- 容错：Checkpoint提供容错和错误恢复：如果一个或多个节点在给定的超级步骤失败，你可以从最后一个成功的步骤重新启动图。
- 待定写入：当一个图节点在给定的超级步骤执行过程中失败时，LangGraph会存储来自在该超级步骤成功完成的任何其他节点的待定checkpoint写入。当你从该超级步骤恢复图执行时，你不会重新运行成功的节点。


## 核心概念
### 线程
线程是分配给checkpointer保存每个checkpoint的**唯一ID或线程标识符**。它包含一系列运行的累积状态。当执行运行时，助手的底层图的状态将持久化到线程。

当使用checkpointer调用图时，你必须在配置的`configurable`部分指定`thread_id`：
```python
{"configurable": {"thread_id": "1"}}
```
可以检索线程的当前和历史状态。要持久化状态，必须在执行运行之前创建一个线程。LangSmith API提供了几个端点，用于创建和管理线程和线程状态。有关更多详细信息，请参阅API参考资料。

**checkpointer使用`thread_id`作为存储和检索checkpoints的主键**。没有它，checkpointers无法保存状态或在中断后恢复执行，因为checkpointers使用thread_id加载保存的状态。

#### 选择如何继续一个线程
thread_id标识保存的状态。输入和`checkpoint_id`确定调用是开始新工作、恢复未完成的工作还是重放历史记录。单独重用线程ID并不意味着执行恢复。

使用checkpointer和现有线程，为你的目标选择调用：
| 目标 | 调用 |  执行|
|---|---|---|
| 提交新输入   | graph.invoke(input, config)  | 将输入应用于已保存状态，并从入口点开始。  |
| 出错后继续   | graph.invoke(None, config)   | 加载最新的checkpoint并重试未完成的工作。省略checkpoint_id。 |
| 回复中断     | graph.invoke(Command(resume=answer), config)  | 提供中断的返回值。被中断的节点重新开始。  |
| 回放历史记录  | graph.invoke(None, snapshot.config)  | 使用get_state_history()中的快照，并在该checkpoint之后重新执行节点。  |

新输入不会清除线程。LangGraph使用state的reducer来应用它。使用新的thread_id则会以空状态开始。

当最新checkpoint没有未完成的工作时，Resume返回保存的结果，而不运行节点。有关可运行的示例，请参阅<a href='/graph-lang/capablities/interrupts'>恢复中断</a>和
<a href='/graph-lang/capablities/time-travel'>重放历史记录</a>。有关包装另一个框架时的入口点恢复规则，请参阅Functional API概述。

### Checkpoints
**线程在特定时间点的状态称为checkpoint**。checkpoint是在每个超级步骤保存的图状态的快照，由`StateSnapshot`对象表示(有关完整字段引用，请参阅StateSnapshot字段)。

#### Super-steps
LangGraph在每个超级步骤边界创建一个checkpoint。超级步骤是图中的一个“滴答”，其中为该步骤调度的所有节点都在执行(可能并行执行)。对于像START->a->B->END这样的顺序图，
输入、节点a和节点B都有单独的超级步骤——在每个步骤之后都会产生一个checkpoint。了解超级步骤边界对于时间旅行很重要，因为你只能从检查点(即超级步骤边界)恢复执行。

除了超级步骤checkpoint，LangGraph还在节点(任务)级别持久化写入。当超级步骤中的每个节点完成时，其输出将作为链接到正在进行的checkpoint的任务条目写入checkpointer的checkpoint_writes表。
这些按任务写入是启用待定写入恢复的原因：如果同一超级步骤中的另一个节点发生故障，成功节点的写入已经持久化，不需要在恢复时重新运行。一旦超级步骤完成，就会提交完整状态快照。

LangGraph还可以在超级步骤中保存单个节点执行的写入。**这些写入被存储为任务并用于容错**：如果同一超级步骤中的另一个节点发生故障，则恢复时不需要重新计算成功的节点写入。
这些任务写入不是完整的StateSnapshot checkpoint，因此时间旅行从超级步骤边界的完整checkpoint恢复。

Checkpoints是持久的，可用于在以后恢复线程的状态。

让我们看看调用简单图时保存了哪些checkpoints，如下所示：
```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langchain_core.runnables import RunnableConfig
from typing import Annotated
from typing_extensions import TypedDict
from operator import add

class State(TypedDict):
    foo: str
    bar: Annotated[list[str], add]

def node_a(state: State):
    return {"foo": "a", "bar": ["a"]}

def node_b(state: State):
    return {"foo": "b", "bar": ["b"]}


workflow = StateGraph(State)
workflow.add_node(node_a)
workflow.add_node(node_b)
workflow.add_edge(START, "node_a")
workflow.add_edge("node_a", "node_b")
workflow.add_edge("node_b", END)

checkpointer = InMemorySaver()
graph = workflow.compile(checkpointer=checkpointer)

config: RunnableConfig = {"configurable": {"thread_id": "1"}}
graph.invoke({"foo": "", "bar":[]}, config)
```
运行图表后，将有4个checkpoints：
- 空Checkpoint，START作为下一个要执行的节点
- Checkpoint，用户输入 `{ 'foo': '', 'bar': [] }` 和node_a作为下一个要执行的节点
- Checkpoint, 输出node_a `{ 'foo': 'a'，'bar': ['a'] }` 和node_b作为下一个要执行的节点
- Checkpoint的输出为node_b `{'foo'： 'b'，'bar'：['a'，'b'] }`， 并且没有要执行的下一个节点

请注意，bar通道值包含来自两个节点的输出，因为此示例具有bar通道的reducer。

#### Checkpoint命名空间
每个checkpoint都有一个checkpoint_ns(checkpoint命名空间)字段，用于标识它属于哪个图或子图：
- ""(空字符串)：checkpoint属于父(根)图。
- "node_name:uuid"：checkpoint属于作为给定节点调用的子图。对于嵌套子图，名称空间用|分隔符连接(例如，“outer_node:uuid|inner_node:uuid”)。

你可以通过配置从节点内访问checkpoint命名空间：
```python
from langchain_core.runnables import RunnableConfig

def my_node(state: State, config: RunnableConfig):
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
    # "" for the parent graph, "node_name:uuid" for a subgraph
```

有关使用子图状态和checkpoint的更多详细信息，请参阅<a href='/graph-lang/capablities/subgraphs'>子图</a>。


## 获取和更新状态

### 获取状态
与保存的图状态交互时，必须指定线程标识符。你可以通过调用graph.get_state(config)来查看图的最新状态。这将返回一个StateSnapshot对象，该对象对应于与配置中提供的线程ID关联的最新checkpoint，
或者与线程的checkpoint ID关联的checkpoint(如果提供的话)。
```python
# get the latest state snapshot
config = {"configurable": {"thread_id": "1"}}
graph.get_state(config)

# get a state snapshot for a specific checkpoint_id
config = {"configurable": {"thread_id": "1", "checkpoint_id": "1ef663ba-28fe-6528-8002-5a559208592c"}}
graph.get_state(config)
```
在这个例子中，get_state的输出如下：
```python
StateSnapshot(
    values={'foo': 'b', 'bar': ['a', 'b']},
    next=(),
    config={'configurable': {'thread_id': '1', 'checkpoint_ns': '', 'checkpoint_id': '1ef663ba-28fe-6528-8002-5a559208592c'}},
    metadata={'source': 'loop', 'writes': {'node_b': {'foo': 'b', 'bar': ['b']}}, 'step': 2},
    created_at='2024-08-29T19:19:38.821749+00:00',
    parent_config={'configurable': {'thread_id': '1', 'checkpoint_ns': '', 'checkpoint_id': '1ef663ba-28f9-6ec4-8001-31981c2c39f8'}},
    tasks=()
)
```
#### 状态快照字段
| 字段 | 类型 |  描述 |
|---|---|---|
| values        | dict             | 此checkpoint的状态通道值。  |
| next          | tuple[str, ...]  | 接下来要执行的节点名称。空`()`表示图已完成。 |
| config        | dict             | 包含`thread_id`, `checkpoint_ns`, 和`checkpoint_id`. |
| metadata      | dict             | 执行元数据.包含`source` `("input", "loop", or "update")`, `writes` (节点输出), 和 `step` (super-step数量).  |
| created_at    | str              | 创建此checkpoint的ISO 8601时间戳。  |
| parent_config | dict             | 上一个checkpoint的配置。第一个checkpoint没有。 |
| tasks         | tuple[PregelTask, ...]  | 此步骤要执行的任务。每个任务都有`id`、`name`、`error`、`interrupts`和可选的`state`(子图快照，当使用`subgraph=True`时)。  |

#### 查找特定checkpoint
你可以过滤状态历史记录，以查找符合特定条件的checkpoint：
```python
history = list(graph.get_state_history(config))

# Find the checkpoint before a specific node executed
before_node_b = next(s for s in history if s.next == ("node_b",))

# Find a checkpoint by step number
step_2 = next(s for s in history if s.metadata["step"] == 2)

# Find checkpoints created by update_state
forks = [s for s in history if s.metadata["source"] == "update"]

# Find the checkpoint where an interrupt occurred
interrupted = next(
    s for s in history
    if s.tasks and any(t.interrupts for t in s.tasks)
)
```

#### 列出每个线程
要查看Checkpointer保存的每个线程的状态，例如构建管理或调试视图，请在列出checkpoint时省略thread_id：

graph.get_statehistory(config)在config中需要一个thread_id，并且只返回一个线程的历史记录。在你传递给编译的同一个checkpointer上调用.list，并且config=None：
```python
# config=None returns checkpoints across every thread
for checkpoint_tuple in checkpointer.list(None):
    print(checkpoint_tuple.config["configurable"]["thread_id"])
```
传递`none`，不是｛｝。`SqliteSaver`将任何非None配置视为线程过滤器，并在缺少`thread_id`时引发。对于异步图，请改用`.alist(None)`。这适用于InMemorySaver、SqliteSaver和PostgresSaver。
`.list`仍然为每个checkpoint返回一行，而不是为每个线程返回一行。因此，你可以自己按thread_id分组以构建线程列表。

### 回放
Replay重新执行前一个checkpoint的步骤。使用之前的checkpoint_id调用图，以在该checkpoint之后重新运行节点。跳过checkpoint之前的节点(其结果已保存)。
checkpoint重新执行后的节点，包括任何LLM调用、API请求或中断，它们在回放期间总是被重新触发。

有关回放过去执行的完整详细信息和代码示例，请参阅<a href='/graph-lang/capablities/time-travel'>时间旅行</a>。

### 更新状态

你可以使用update_state编辑图形状态。这将创建一个具有更新值的新checkpoint，而不会修改原始checkpoint。更新被视为与节点更新相同：值在定义时通过reducer函数传递，因此具有reducer的通道会累积值而不是覆盖它们。

你可以选择指定as_node来控制更新来自哪个节点，这会影响下一个执行的节点。有关详细信息，请参阅时间旅行：as_node。

## 持久化模式
LangGraph支持三种持久化模式，使你能够平衡性能和数据一致性。你可以在调用任何图执行方法时指定持久化模式：
```python
graph.stream(
    {"input": "test"},
    durability="sync"
)
```
从最不持久到最持久的持久化模式如下：
- 退出：LangGraph仅在图执行退出时(成功退出、出现错误或由于人在循环中断)才保留更改。这为长时间运行的图提供了最佳性能，但意味着中间状态不会被保存，因此你无法在执行过程中从系统故障(如进程崩溃)中恢复。
- 异步：LangGraph在执行下一步时异步保存更改。这提供了良好的性能和持久性，但如果进程在执行过程中崩溃，LangGraph不写入checkpoints的风险很小。
- 同步：LangGraph在下一步开始之前同步保存更改。这确保了LangGraph在继续执行之前写入每个checkpoints，以牺牲一些性能开销为代价提供了高持久性。

### 新线程上的第一个持久checkpoint
对于新线程，持久化模式还确定在第一个用户节点执行之前提交哪些checkpoint。内部__start__超级步首先运行；步骤0是在该超级步骤之后写入的循环checkpoint。
- 退出：在运行结束之前不存在checkpoint。运行过程中的崩溃不会留下线程的记录。
- 异步：LangGraph在第一个用户节点执行之前开始写入输入checkpoint，但不会等待写入完成。第一个用户节点可以在提交任何checkpoint之前运行。
- 同步：LangGraph在第一个用户节点执行之前提交输入checkpoint(步骤-1)和步骤0checkpoint。

:::warning
<small>
在每种模式下，第一个checkpoint变得持久之前的崩溃会使线程与从未被调用的线程无法区分：get_tuple()在这两种情况下都返回None，invoke(None，config)会引发EmptyInputError。
如果需要区分“从未接受”和“已接受但丢失”，请在checkpointer之外记录准入，例如在调用invoke之前将发件箱行提交到自己的存储中。
</small>
:::

## 优化checkpoint存储
默认情况下，LangGraph checkpoint在每个超级步骤写入每个状态通道的完整值。对于具有大量累积的长时间运行的线程(如多轮对话)，这可能会随着时间的推移产生显著的存储增长。

`DeltaChannel`只存储增长的增量，而不是完整的累积值，从而大大减少了附加重通道的checkpoint大小。有关使用情况和存储与延迟的权衡，请参阅DeltaChannel。

:::warning
<small>
DeltaChannel要求langgraph>=1.2，目前处于beta(测试阶段)。API可能会在未来版本中更改。
</small>
:::


## Checkpointer库
在幕后，checkpoint是由符合BaseCheckpointSaver接口的checkpointer对象驱动的。LangGraph提供了几个checkpointer实现，所有这些实现都是通过独立的、可安装的库实现的。这里推荐`langgraph-checkpoint-postgres`.

:::info
<small>
请参阅可用提供程序的checkpointer集成。
</small>
:::

- langgraph-checkpoint：checkpointer存储基础接口(BaseCheckpointSaver)和序列化/反序列化接口(SerializerProtocol)。包括用于实验的内存中checkpointer实现(InMemorySaver)。LangGraph附带了LangGraph checkpoint。
- langgraph-checkpoint-sqlite：使用sqlite数据库的langgraph checkpointer的实现(SqliteSaver/AsyncSqliteSaver)。非常适合实验和本地工作流程。需要单独安装。
- langgraph-checkpoint-postgres：一个使用postgres数据库(PostgresSaver/AsyncPostgresSaver)的高级checkpointer，用于LangSmith。非常适合在生产中使用。需要单独安装。
- langgraph-checkpoint-mongodb：一个使用mongodb的高级checkpoint(MongoDBSaver/AsyncMongoDBSaver)。非常适合在生产中使用。需要单独安装。
- langchain-azure-cosmossdb：LangGraph checkpointer的一种实现，它使用NoSQL数据库azure Cosmos DB(CosmosDBSaverSync/CosmosDBSaver)。非常适合在Azure的生产环境中使用。
  支持同步和异步操作，使用Microsoft Entra ID身份验证。需要单独安装。

### Checkpointer接口
每个checkpointer都符合BaseCheckpointSaver接口，并实现了以下方法：
- .put-存储checkpoint及其配置和元数据。
- .put_writes-存储链接到checkpoint的中间写入(即 pending writes)。
- .get_tuple-使用给定的配置(thread_id和checkpoint_id)获取checkpoint元组。这用于在graph.get_state()中填充StateSnapshot。
- .list-列出与给定配置和筛选条件匹配的checkpoints。这用于填充graph.get_state_history()中的状态历史。传递config=None以列出每个线程的checkpoint。请参阅列出每个线程。

如果checkpoint用于异步图执行(即通过.ainvoke、.astream、.abatch执行图)，则将使用上述方法的异步版本(.aput、.aput_writes、.aget_tuple、.list)。

:::info
<small>
为了异步运行图，你可以使用InMemorySaver，或异步版本的Sqlite/Postgres checkpointer——AsyncSqliteSaver/AsyncPostgresSaver checkpointer。
</small>
:::

### 序列化器
当checkpointer保存图状态时，它们需要序列化状态中的通道值。这是使用序列化器对象完成的。

`langgraph_checkpoint`定义了实现序列化器的协议。它提供了一个默认实现(`JsonPlusSerializer`)，可以处理各种类型，包括LangChain和langgraph原语、日期时间、枚举等。

#### 使用pickle进行序列化
默认的序列化器`JsonPlusSerializer`在底层使用ormsgpack和JSON，这并不适用于所有类型的对象。

如果你想为msgpack编码器当前不支持的对象(如Pandas数据帧)回退到pickle，你可以使用`JsonPlusSerializer`的pickle_fallback参数：
```python
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.checkpoint.serde.jsonplus import JsonPlusSerializer

# ... Define the graph ...
graph.compile(
    checkpointer=InMemorySaver(serde=JsonPlusSerializer(pickle_fallback=True))
)
```
#### 加密
checkpointers可以选择加密所有持久状态。要启用此功能，请将`EncryptedSerialier`的实例传递给任何`BaseCheckpointSaver`实现的`serde`参数。创建加密序列化器的最简单方法是通过`from_pycryptodome_aes`，
它从`LANGRAPH_aes_key`环境变量读取aes密钥(或接受密钥参数)：
```python
import sqlite3

from langgraph.checkpoint.serde.encrypted import EncryptedSerializer
from langgraph.checkpoint.sqlite import SqliteSaver

serde = EncryptedSerializer.from_pycryptodome_aes()  # reads LANGGRAPH_AES_KEY
checkpointer = SqliteSaver(sqlite3.connect("checkpoint.db"), serde=serde)
```
```python
from langgraph.checkpoint.serde.encrypted import EncryptedSerializer
from langgraph.checkpoint.postgres import PostgresSaver

serde = EncryptedSerializer.from_pycryptodome_aes()
checkpointer = PostgresSaver.from_conn_string("postgresql://...", serde=serde)
checkpointer.setup()
```

在LangSmith上运行时，只要存在`LANGRAPH_AES_KEY`，加密就会自动启用，因此你只需要提供环境变量。通过实现`CipherProtocol`并将其提供给`EncryptedSerialier`，可以使用其他加密方案。

## 构建自定义checkpointer

:::tip
<small>
使用一致性测试套件在构建时验证你的实现。它涵盖了所有五种基本方法和扩展功能，包括增量通道。发货前在CI中运行它。
</small>
:::

本节介绍为自定义存储后端从头开始实现BaseCheckpointSaver。如果你已经有一个可用的checkpointer，只需要添加增量通道支持，请跳到增量通道支持。

### 概述
LangGraph的持久层建立在两个存储抽象之上：
- Checkpoints表——每个超级步骤一行；存储序列化的图状态(channel_values、channel_versions、versionsseed)并链接到其父checkpoint。
- 写入表——在一个超级步骤中，每个节点输出一行；存储链接到checkpoint的(task_id、channel、value)元组。

你的checkpointer管理这两个表。put写入检查点行；put_writes写入节点输出行；get_tuple将两者都读回CheckpointTuple

### 基础合同
子类`BaseCheckpointSaver`并实现这五个方法。所有这些都是必需的——缺少基方法会在运行时引发NotImplementedError。
```python
from collections.abc import AsyncIterator, Iterator, Sequence
from typing import Any
from langchain_core.runnables import RunnableConfig
from langgraph.checkpoint.base import (
    BaseCheckpointSaver,
    ChannelVersions,
    Checkpoint,
    CheckpointMetadata,
    CheckpointTuple,
)

class MyCheckpointer(BaseCheckpointSaver):
    async def aput(
        self,
        config: RunnableConfig,
        checkpoint: Checkpoint,
        metadata: CheckpointMetadata,
        new_versions: ChannelVersions,
    ) -> RunnableConfig:
        ...

    async def aput_writes(
        self,
        config: RunnableConfig,
        writes: Sequence[tuple[str, Any]],
        task_id: str,
        task_path: str = "",
    ) -> None:
        ...

    async def aget_tuple(self, config: RunnableConfig) -> CheckpointTuple | None:
        ...

    async def alist(
        self,
        config: RunnableConfig | None,
        *,
        filter: dict[str, Any] | None = None,
        before: RunnableConfig | None = None,
        limit: int | None = None,
    ) -> AsyncIterator[CheckpointTuple]:
        ...
        yield  # make this an async generator

    async def adelete_thread(self, thread_id: str) -> None:
        ...
```

#### put/aput
存储一个checkpoint行。使用存储的checkpoint_id返回更新的配置。
关键要求：
- 使用`self.serde.dumps_typed(checkpoint)`序列化checkpoint——这将处理所有LangGraph原生类型，包括增量通道使用的`_DeltaSnapshot blob`。
- 完整存储元数据——不要删除未知密钥。LangGraph在minor版本中添加了新的元数据字段(例如增量通道的counter_since_delta_snapshot)；默默地丢弃它们会破坏特征。
- 将config[“configurable”].get(“checkpoint_id”)存储为checkpoint ID，以便`get_tuple`可以填充`parent_config`。

```python
async def aput(self, config, checkpoint, metadata, new_versions):
    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
    checkpoint_id = checkpoint["id"]
    parent_id = config["configurable"].get("checkpoint_id")

    type_, blob = self.serde.dumps_typed(checkpoint)
    serialized_metadata = self.serde.dumps_typed(metadata)

    await self.db.execute(
        "INSERT INTO checkpoints (...) VALUES (...)",
        thread_id, checkpoint_ns, checkpoint_id, parent_id,
        type_, blob, *serialized_metadata,
    )
    return {
        "configurable": {
            "thread_id": thread_id,
            "checkpoint_ns": checkpoint_ns,
            "checkpoint_id": checkpoint_id,
        }
    }
```

#### put_writes/aput_writes
在当前超级步骤中存储单个任务的节点输出行。这些行通过(thread_id，checkpoint_ns，checkpoint_id)链接到checkpoint。
```python
async def aput_writes(self, config, writes, task_id, task_path=""):
    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"]["checkpoint_ns"]
    checkpoint_id = config["configurable"]["checkpoint_id"]

    rows = []
    for idx, (channel, value) in enumerate(writes):
        type_, blob = self.serde.dumps_typed(value)
        final_idx = WRITES_IDX_MAP.get(channel, idx)
        rows.append((thread_id, checkpoint_ns, checkpoint_id,
                      task_id, task_path, final_idx, channel, type_, blob))

    await self.db.executemany("INSERT INTO writes (...) VALUES (...)", rows)
```
从`langgraph.checkpoint.base`导入`WRITES_IDX_MAP`。它将特殊通道(__error_、__interrupt_等)映射到保留的负索引，这样它们就不会与常规写入索引冲突。

#### get_tuple/aget_tuple
检索checkpoint。配置可能包含：
- 没有checkpoint_id--返回线程+命名空间的最新checkpoint。
- 一个特定的checkpoint_id——返回该确切的checkpoint。

两条路径都必须正常工作。特定的id路径用于时间旅行，关键是用于每次图调用时的增量通道状态重建(请参阅增量通道支持)。断开的特定id查找会默默地破坏增量通道状态。
```python
async def aget_tuple(self, config):
    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"].get("checkpoint_ns", "")
    checkpoint_id = config["configurable"].get("checkpoint_id")

    if checkpoint_id:
        row = await self.db.fetchone(
            "SELECT * FROM checkpoints "
            "WHERE thread_id=? AND checkpoint_ns=? AND checkpoint_id=?",
            thread_id, checkpoint_ns, checkpoint_id,
        )
    else:
        row = await self.db.fetchone(
            "SELECT * FROM checkpoints "
            "WHERE thread_id=? AND checkpoint_ns=? "
            "ORDER BY checkpoint_id DESC LIMIT 1",
            thread_id, checkpoint_ns,
        )

    if row is None:
        return None

    writes = await self.db.fetchall(
        "SELECT task_id, channel, type, value FROM writes "
        "WHERE thread_id=? AND checkpoint_ns=? AND checkpoint_id=? "
        "ORDER BY task_id, idx",
        thread_id, checkpoint_ns, row["checkpoint_id"],
    )
    pending_writes = [
        (w["task_id"], w["channel"], self.serde.loads_typed((w["type"], w["value"])))
        for w in writes
    ]

    checkpoint = self.serde.loads_typed((row["type"], row["blob"]))
    metadata = self.serde.loads_typed((row["metadata_type"], row["metadata"]))

    parent_config = None
    if row["parent_checkpoint_id"]:
        parent_config = {
            "configurable": {
                "thread_id": thread_id,
                "checkpoint_ns": checkpoint_ns,
                "checkpoint_id": row["parent_checkpoint_id"],
            }
        }

    return CheckpointTuple(
        config={
            "configurable": {
                "thread_id": thread_id,
                "checkpoint_ns": checkpoint_ns,
                "checkpoint_id": row["checkpoint_id"],
            }
        },
        checkpoint=checkpoint,
        metadata=metadata,
        parent_config=parent_config,
        pending_writes=pending_writes,
    )
```

:::warning
<small>
行键/索引设计对特定的id查找很重要。如果你的存储使用不嵌入checkpoint_id的时间顺序键(例如，反向时间戳)，则无法按id进行直接行读取。你必须在行键中编码checkpoint_id，或构建辅助索引。
在每次查找时使用值过滤器进行扫描是有效的，但不会缩放。
</small>
:::

#### list/alist
返回线程的checkpoint，最新的优先。尊重`before`(只返回比该配置的checkpoint_id旧的checkpoint)和`limit`

#### delete_thread/adelete_thread
删除线程的所有checkpoints和写入。必须删除checkpoint行和写入行

### 行key/index设计
如何存储和索引checkpoint直接影响正确性和性能。

推荐schema(SQL)：
```python
CREATE TABLE checkpoints (
    thread_id          TEXT NOT NULL,
    checkpoint_ns      TEXT NOT NULL DEFAULT '',
    checkpoint_id      TEXT NOT NULL,   -- ULID, lexicographically sortable newest-last
    parent_checkpoint_id TEXT,
    type               TEXT,
    checkpoint         BYTEA,
    metadata           JSONB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);

CREATE TABLE writes (
    thread_id     TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    task_id       TEXT NOT NULL,
    task_path     TEXT NOT NULL DEFAULT '',
    idx           INTEGER NOT NULL,
    channel       TEXT NOT NULL,
    type          TEXT,
    value         BYTEA,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id, task_id, task_path, idx)
);
```

因为`checkpoint_id`是一个ULID，所以它按字典顺序排序——值越大，越新。“获取最新”是`ORDER BY checkpoint_id DESC LIMIT 1`；“get by id”是对主键的相等性查找。

对于非SQL存储：同样的原则适用。无论你使用什么密钥方案，直接查找(thread_id，checkpoint_ns，checkpoint_id)必须是O(1)或接近它。避免按id查找checkpoint的唯一方法是扫描线程的所有行的设计。

### 序列化
checkpoint、写入和元数据始终使用`self.serde`(继承自BaseCheckpointSaver，默认为JsonPlusSerializer)。不要直接将pickle用于元数据——它确实有效，但JsonPlusSerializer可以产生人类可读的输出，并更好地处理版本控制。

`JsonPlusSerializer`自动处理所有LangGraph原生类型：
- _DeltaSnapshot——增量通道使用的哨兵blob(msgpack ext code 7)
- Pydantic v2模型、数据类、numpy数组、日期时间、枚举等

如果编写自定义序列化程序，请确保它可以从langgraph.checkpoint.serde.types往返_DeltaSnapshot。

### 扩展功能
这些方法是可选的，但可以解锁agent服务器的其他功能。如果你的存储后端能够有效地支持它们，请实施它们。
|  Method | What it enables |
|---|---|
| adelete_for_runs | 回滚多任务策略  |
| acopy_thread     | 高效的线程分叉  |
| aprune           | 线程历史修剪  |
| aget_delta_channel_history | 高效的delta信道状态重建(见下文) |

agent服务器在启动时自动检测检查指针实现了哪些功能，并激活相应的功能。

### Delta通道支持

:::info
<small>
DeltaChannel处于测试阶段。当设计稳定时，API和磁盘上表示可能会发生变化。
</small>
:::

DeltaChannel是一个reducer通道，它只在checkpoint blob中存储一个哨兵(MISSING)，而不是完整的通道值。状态是通过还原器重放祖先写入来重建的。
这使得checkpoint斑点每一步为O(1)，而不是随着时间的推移累积的消息等通道的O(N)。

#### 运行时需要什么
当加载channel_values中缺少增量通道的checkpoint时，LangGraph调用`saver.get_delta_channel_history(config=config，channels=[…])`。对于每个通道，这将返回：
- writes——所有对祖先链中该通道的写入，从最早的开始，直到最近的快照。
- seed(可选)——存储在最近祖先处的_DeltaSnapshot blob，该祖先有一个；如果遍历到达根目录时没有找到快照，则不存在。

然后，运行时调用channel.from_checkpoint(种子)和channel.replay_writes(写入)来重建实时值。

#### 默认实现
`BaseCheckpointSaver`提供了一个默认的`get_delta_channel_history`，它适用于任何正确的`get_tuple`实现：
```python
# Simplified from BaseCheckpointSaver
def get_delta_channel_history(self, *, config, channels):
    target = self.get_tuple(config)          # load the head checkpoint
    cursor = target.parent_config            # walk from its parent
    collected = {ch: [] for ch in channels}
    seed = {}
    remaining = set(channels)

    while cursor and remaining:
        tup = self.get_tuple(cursor)         # ← requires correct by-id lookup
        if tup is None:
            break
        for write in reversed(tup.pending_writes or []):
            if write[1] in remaining:
                collected[write[1]].append(write)
        for ch in list(remaining):
            if ch in tup.checkpoint["channel_values"]:
                seed[ch] = tup.checkpoint["channel_values"][ch]
                remaining.discard(ch)
        cursor = tup.parent_config

    return {
        ch: {"writes": list(reversed(collected[ch])), **({"seed": seed[ch]} if ch in seed else {})}
        for ch in channels
    }
```

**关键依赖关系**：get_tuple(cursor)总是使用特定的checkpoint_id(父节点的id)调用。如果该查找返回None，则行走将立即停止，每个增量通道都将重建为空，并且不会出现任何错误。这就是为什么`get_tuple`中的特定id路径必须正确。

#### 性能覆盖

默认的walk为每个祖先checkpoint发出一个get_tuple调用。对于具有良好查询支持的后端，重写`get_delta_channel_history`(及其异步双胞胎)以检索祖先链，并写入两个查询：
```python
async def aget_delta_channel_history(self, *, config, channels):
    if not channels:
        return {}

    thread_id = config["configurable"]["thread_id"]
    checkpoint_ns = config["configurable"].get("checkpoint_ns", "")
    checkpoint_id = config["configurable"]["checkpoint_id"]

    # Stage 1: stream ancestors newest-first until every channel has a seed
    ancestors = await self.db.fetchall(
        "SELECT checkpoint_id, parent_checkpoint_id, type, checkpoint "
        "FROM checkpoints "
        "WHERE thread_id=? AND checkpoint_ns=? AND checkpoint_id < ? "
        "ORDER BY checkpoint_id DESC",
        thread_id, checkpoint_ns, checkpoint_id,
    )

    chain_by_ch: dict[str, list[str]] = {ch: [] for ch in channels}
    seed_by_ch: dict[str, Any] = {}
    remaining = set(channels)
    cur_id = config["configurable"]["checkpoint_id"]

    for row in ancestors:
        if not remaining:
            break
        parent_id = row["parent_checkpoint_id"]
        ckpt = self.serde.loads_typed((row["type"], row["checkpoint"]))
        cv = ckpt.get("channel_values") or {}
        for ch in list(remaining):
            chain_by_ch[ch].append(row["checkpoint_id"])
            if ch in cv:
                seed_by_ch[ch] = cv[ch]
                remaining.discard(ch)
        cur_id = parent_id

    # Stage 2: fetch writes for each channel's ancestor chain in one query
    result: dict[str, DeltaChannelHistory] = {}
    for ch in channels:
        chain = chain_by_ch[ch]
        if not chain:
            entry: DeltaChannelHistory = {"writes": []}
            if ch in seed_by_ch:
                entry["seed"] = seed_by_ch[ch]
            result[ch] = entry
            continue

        write_rows = await self.db.fetchall(
            f"SELECT checkpoint_id, task_id, idx, type, value FROM writes "
            f"WHERE thread_id=? AND checkpoint_ns=? AND channel=? "
            f"AND checkpoint_id IN ({','.join('?' * len(chain))})"
            f"ORDER BY checkpoint_id, task_id, idx",
            thread_id, checkpoint_ns, ch, *chain,
        )
        writes_by_cid: dict[str, list[PendingWrite]] = {}
        for row in write_rows:
            cid = row["checkpoint_id"]
            value = self.serde.loads_typed((row["type"], row["value"]))
            writes_by_cid.setdefault(cid, []).append((row["task_id"], ch, value))

        # chain is newest-first; iterate oldest-first to get correct replay order
        collected: list[PendingWrite] = []
        for cid in reversed(chain):
            collected.extend(writes_by_cid.get(cid, []))

        entry = {"writes": collected}
        if ch in seed_by_ch:
            entry["seed"] = seed_by_ch[ch]
        result[ch] = entry

    return result
```
